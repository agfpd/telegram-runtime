# 06 — Интеграция и установка

**Русский** · [English](../06-integration.md)

## Место в iapeer

telegram-runtime — это `*-runtime` пакет экосистемы [iapeer](https://github.com/agfpd/iapeer): рантайм присутствия для пиров-людей, наравне с агентскими рантаймами Claude и Codex. iapeer ставит и онбордит его как любой рантайм-пакет.

Пакет регистрируется манифестом рантайма (`runtime.json`), по которому iapeer знает, как его запускать и настраивать. У telegram-рантайма **нет заранее объявленного набора пиров** — это режим «добавляет оператор»: людей заводят по одному командой `iapeer create <имя> --runtime telegram`, в отличие от рантаймов с фиксированным набором (например планировщик).

## Установка и обновление

```bash
npx @agfpd/telegram-runtime       # установить (бинарь + манифест)
iapeer install-runtime telegram   # то же средствами iapeer
iapeer update-runtime telegram    # обновить с перезапуском пиров рантайма
```

Установка идемпотентна: замены бинаря и манифеста по отдельности атомарны.
Манифест сначала подготавливается во временном файле, прежний бинарь сохраняется
до успешной публикации пары и восстанавливается при синхронной ошибке публикации.
Это не атомарная транзакция двух путей при потере питания. При провижне каждого
пира iapeer вызывает хук настройки (`self-config`), который дописывает привязки
Telegram и, если есть, учётные данные бота.

### Проверка подписи исполняемого файла на macOS

И компиляция, и copy-self сначала создают временный файл рядом с целевым бинарём.
После `chmod`, **до замены установленного бинаря и записи манифеста**, установщик
проверяет этот файл командой `/usr/bin/codesign --verify --deep --strict`.
Валидная подпись остаётся без изменений, сохраняя идентичность подписанта.
Невалидная подпись исправляется командой `/usr/bin/codesign --force --sign -` и
обязана пройти повторную строгую проверку. Отсутствующий или убитый проверяющий
процесс, ошибка подписи либо неуспех повторной проверки прерывают установку:
временный файл удаляется, прежние бинарь и манифест остаются нетронутыми.
На других платформах эта проверка пропускается. Контракт реализован локально;
прямая установка через `npx` не зависит от signing-helper ядра.

Флаги строгой проверки соответствуют [рекомендациям Apple](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/Procedures/Procedures.html).
Они проверяют подпись, а не notarization или доверие Gatekeeper к дистрибутиву.

Архив содержит runtime-зависимости и [автономную проверку установки](../../scripts/verify-install.md).
Настоящая установка, отказ codesign и изолированное восстановление актуального
резерва повторяются без checkout, npm-кэша и сети. Исполнение CLI не заменяет
приёмку Telegram и супервизора опроса.

Перед согласованным обновлением хоста нужно сохранить текущий работоспособный
бинарь, прошедший строгую проверку, вместе с его манифестом. При неуспехе
поведенческой приёмки восстанавливается **эта пара**, затем Telegram-пир
перезапускается через `iapeer stop` / `iapeer start`. Откат через старый установщик
без проверки подписи недопустим. Активация и откат перезапускают весь мост;
их координирует администратор хоста, оставляя web резервным каналом.

## Как мост встроен в обмен сообщениями

Мост сидит на стыке двух миров:

- со стороны **Telegram** он опрашивает ботов и шлёт им сообщения;
- со стороны **iapeer** он получает исходящие от пиров (как сообщения для доставки) и доставляет входящие пиру-адресату средствами iapeer.

Поэтому он не маршрутизирует сам — маршрутизацию между пирами делает демон iapeer; мост лишь переводит между Telegram и протоколом iapeer. Команды управления из чата мост исполняет через управляющие команды iapeer: `/stop` — через `iapeer interrupt` (прервать ход), `/new` и `/compact` — через одноимённые команды.

## Здоровье опроса и контракт мониторинга

Живой процесс и рабочая исходящая доставка не доказывают, что входящий long
poll продвигается. Поэтому мост надзирает за каждым ботом отдельно. Ответ
`getUpdates` целиком читается в пределах жёсткого дедлайна, включая тело; если
запрос его превысил, останавливается и заменяется только поколение grammY этого
бота. Остальные поллеры и исходящая доставка продолжают работать.

Начальная настройка тоже под надзором: `getMe` и `deleteWebhook` имеют сквозной
дедлайн 30 с, включая разбор ответа. Их ошибки обходят скрытый цикл повторов
grammY; повторяет весь запуск наш супервизор с задержкой 1–15 с. До 0.28.8 после
сетевого сбоя новое поколение могло часами спать внутри `Bot.start()`, ещё не
дойдя до защищённого `getUpdates`. Независимый watchdog запуска ждёт на 5 с
дольше дедлайна настройки. Если остановка поколения И завершение его `start()`
не укладываются в ограждение (по умолчанию 15 с), процесс пишет `poll.fatal` и
выходит с ненулевым кодом для перезапуска хостовым супервизором. Новое поколение
не запускается рядом с неограждённым. Неожиданный штатный выход тоже повторяется.

Структурные строки в stderr начинаются с `telegram-runtime polling `. JSON
нужно отслеживать по `botKey` и `generation`:

| Событие | Значение |
|---|---|
| `poll.boot` | поколение начинает настройку; это ещё не доказательство опроса |
| `poll.bootstrap.error` | ограниченный по времени сбой `getMe`/`deleteWebhook`: метод, длительность, флаг таймаута |
| `poll.start.timeout` | независимый watchdog запуска не дождался `onStart` |
| `poll.start` | поколение бота вошло в long polling |
| `poll.heartbeat` | здоровые завершённые циклы; `emptyCycles` явно считает штатные пустые long poll, а `updates` — полученные обновления |
| `poll.error` | транспортный сбой или неуспешный/невалидный ответ Bot API (не чаще одной строки в минуту на поколение); это не здоровый heartbeat |
| `poll.stalled` | один `getUpdates` превысил `deadlineMs`; это повод для алёрта, после него запускается самовосстановление |
| `poll.restart` | зависшее поколение ограждено, следующим стартует новое |
| `poll.failed` | поколение завершилось ошибкой и будет повторено с backoff |
| `poll.fatal` | поколение не удалось оградить; процесс выходит с ненулевым кодом вместо тихого зомби |

Монитор должен немедленно алертить по `poll.stalled` и требовать после него
`poll.restart`, затем `poll.start` И `poll.heartbeat` того же `botKey`.
Сам `poll.restart` — только попытка, не доказательство восстановления. Сигналы
`poll.start.timeout`/`poll.fatal` и повторяющиеся ошибки настройки требуют алёрта.
Дополнительный алёрт — у
стартовавшего бота нет `poll.heartbeat` дольше суммы настроенного интервала
heartbeat и дедлайна зависания. Отсутствие пользовательских сообщений не служит
проверкой здоровья: незанятый бот подтверждает жизнь счётчиком `emptyCycles`.

## Зависимости

| Зависимость | Обязательность | Без неё |
|---|---|---|
| iapeer | обязательна | мост не работает: некуда доставлять входящие, неоткуда брать исходящие и привязки |
| бот Telegram (токен от `@BotFather`) | обязательна | нет канала в Telegram |
| сервис распознавания речи | опциональна | голосовые доезжают файлом, без расшифровки в текст |

## Что вне области

Мост сознательно не делает: не работает через веб-хуки (только опрос), не редактирует и не удаляет отправленные сообщения, не обслуживает групповые чаты и не хранит историю переписки, не объединяет несколько хостов. Это мост «человек ↔ его команда агентов» на одном хосте, а не платформа для Telegram-ботов вообще.
